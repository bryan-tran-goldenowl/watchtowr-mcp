## [0.1.2]

### Changed

- **Submodule URL** — `watchtowr-api-sdk` now points to
  `https://github.com/watchtowr/watchtowr-api-sdk-python.git`. Existing clones must
  follow the migration steps in `README.md` (submodule sync → deinit → remove cached
  module → re-init → `uv sync`).

### Fixed: SDK Compatibility Layer (`watchtowr_mcp_server/sdk_compat.py`)

**Problem**

The `watchtowr-api-sdk` is auto-generated from the watchTowr Platform OpenAPI
specification using OpenAPI Generator. Several fields in the generated Pydantic
models are declared as required (non-nullable) even though the live Platform API
legitimately returns `null` for them in normal operation. Pydantic v2 performs
strict validation on deserialization and hard-fails the moment it encounters a
`null` value for a field it believes is required.

This caused every tool that calls `get_list_findings` — including
`get_findings_summary_by_severity`, `list_findings_by_severity`,
`search_findings`, `list_cisa_kev_findings`, and all composite tools that build
on top of them — to return an error whenever the API response contained a finding
with an in-progress retest or a paginated response on its first/last page.

The specific validation errors encountered:

| SDK Model | Field | Root cause |
|---|---|---|
| `FindingRetestResponseDto` | `completed_at` | `null` when a retest has not yet completed |
| `FindingRetestResponseDto` | `evidence` | `null` when a retest has not yet completed |
| `Retest` | `current_retest.completed_at` / `current_retest.evidence` | Nested DTO still used the original unpatched class due to Pydantic v2 caching type references at class-definition time |
| `ClientFinding` | `created_at` | Live API returns an ISO 8601 string; generated model validator expected a `dict` |
| `Link` | `previous` | `null` on the first page of any paginated response |
| `Link` | `next` | `null` on the last page of any paginated response |

**Why monkey-patching instead of editing the SDK directly**

The `watchtowr-api-sdk` repository is fully auto-generated by OpenAPI Generator
from the Platform's OpenAPI spec. Any manual edits to that repo would be
overwritten the next time the SDK is regenerated from the spec. Modifying the
generated source is therefore not a viable long-term fix.

**Why `model_rebuild(force=True)` alone was not enough**

The natural Pydantic v2 approach — replace the module-level class name and call
`model_rebuild(force=True)` to re-resolve type annotations — does not work here
because Pydantic v2 compiles field validators against the actual class objects at
class-definition time, not against the string names. After class definition, the
validators hold direct references to the original class. `model_rebuild` only
re-resolves *forward references* (string annotations); already-resolved
references are not updated.

**What `sdk_compat.py` does**

`sdk_compat.py` applies targeted runtime patches before any tool registers or
any API call is made:

1. **`FindingRetestResponseDtoCompat`** — a drop-in Pydantic model that mirrors
   `FindingRetestResponseDto` but declares `completed_at` and `evidence` as
   `Optional`, accepting `null` from the API.

2. **`Retest.from_dict` override** — replaces the generated `from_dict` with one
   that uses `model_construct` (bypasses Pydantic's cached field validators) and
   explicitly routes `current_retest` through `FindingRetestResponseDtoCompat`
   so the nullable fields are accepted.

3. **`ClientFinding.from_dict` override** — replaces the generated `from_dict`
   with one that uses `model_construct`, avoiding re-validation of fields like
   `created_at` whose generated type annotation does not match the raw API value.

4. **`Link.from_dict` override** — replaces the generated `from_dict` with one
   that uses `model_construct` so `previous` and `next` can be `null` without
   raising a validation error.

`apply_watchtowr_sdk_compat_patches()` is called at the very start of `main()`
in `mcp.py`, before any tools are registered, ensuring all patches are in place
before the first API call.

**Permanent fix (coming soon)**

The root cause is in the OpenAPI specification: the fields listed above need to
be marked as `nullable: true`. Once the spec is corrected and the SDK is
regenerated, `sdk_compat.py` and the `mcp.py` call to
`apply_watchtowr_sdk_compat_patches()` can be removed.

> A patch to the `watchtowr-api-sdk` OpenAPI spec is planned and will be
> released in an upcoming SDK update.

## [0.1.1]

### Fixed: Severity Normalisation

The Platform API requires severity filter values to be lowercase (`critical`,
`high`, `medium`, `low`). Callers and users frequently pass title-case values
(`Critical`, `High`, etc.) which the API rejects with a `400 Severities not
valid!` error.

Added `normalize_severities()` in `client.py` to lowercase and strip whitespace
from severity strings before they reach the API. All tools that accept a
`severities` parameter now route through this helper so the API call succeeds
regardless of the casing the caller provides.

**Affected tools:** `list_findings_by_severity`, `search_findings`,
`get_unresolved_findings_by_business_unit`, and any composite tool that accepts
a `severities` argument.
